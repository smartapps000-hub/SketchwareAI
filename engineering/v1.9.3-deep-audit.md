## 1. Logic editor drag bar: Copy stayed white (fixed)

`com.besome.sketch.editor.logic.LogicTopMenu` (precompiled) repaints an item when a dragged block enters or leaves it:
inactive = `#FEFEFE` background, `#7D7D7D` text. The method → item mapping, read from the bytecode:
`a(boolean)` → fields `c, d, n` (Copy), `b(boolean)` → `a, b, m` (Delete), `c(boolean)` → `g, h, p`, `d(boolean)` →
`e, f, o`; `e(boolean)` only changes visibility. v1.9.2's `ObLogicTopMenu` restyled `a, b, m` after `a(boolean)`, so
the item `a(boolean)` had just painted white (Copy) stayed white. v1.9.3 pairs each override with the item its super
method paints. Activity: **not run** here.

## 2. Java → blocks against the palette

How it works since v1.9.1: `StatementBlocks` reads each block's code from the generator itself (a.a.a.Fx with marker
values), so there is no separate block table to keep in sync with `block.json`/`Blocks.java`: a palette block becomes a
mapping when its opcode is in `REPORTERS` / `STATEMENTS` and the generator writes it as one line.

`int` / `long` / `float` locals: still custom variables (`private int x;`, the assignment kept as code). A Number
variable is a Java `double`: `String.valueOf(x)` shows `3.0`, `list.get(x)`, `switch (x)`, `array[x]` and int method
parameters stop compiling, and the converter's proof (regenerate and compare the text) cannot see a type change. Making
them Number variables needs either the owner's go to accept that, or a use check (every use of the name in a context
where a double behaves the same), which is the safe way to do it.

No vacant sockets: true / false literals are true / false blocks since v1.9.1 and older saves are repaired when an event
opens (`literalBooleansToBlocks`); a slot is filled only when its value converts, otherwise the whole line stays code.

## 3. Direct XML editing: feasibility and plan

- What exists: the design canvas edits `eC.c` (ViewBean per view: type, id, layout params, properties, `inject` for
  extra attributes); `Ox` writes the XML from it at every build; `ViewEditor` / `ViewPane` are precompiled.
- The Java editor's method fits XML too: XML → ViewBeans is the reverse of `Ox`; it must be proved like Java (generate
  the XML from the new ViewBeans and compare with the typed text; refuse what it can't give back exactly, nothing changed).
- Plan (about 3-4 days + phone test): (1) `XmlToViews` parser (XmlPullParser) for the palette's view types and the
  attributes `Ox` writes, unknown attributes into `inject`; (2) proof by regeneration through `Ox`; (3) a Code-tab style
  screen `XmlEditorActivity` (sora-editor, XML language) opened from the design editor; (4) ART fixture: every template
  project's layouts open and save unchanged, then edits (move a view, change a property, add an attribute) map back;
  (5) layoutlib render of the result. Canvas → XML already works (the build's XML).
