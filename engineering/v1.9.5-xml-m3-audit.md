# v1.9.5 audit: layout XML generation and Material 3 (2 Nov 2026)

Owner's directive "AUDIT & MODERNIZE LAYOUT XML GENERATION & MATERIAL 3 STYLES". Facts from the source, the precompiled jars
(javap) and fixture 908's layout as the v1.9.4 release APK generated it (`mysc/908/.../layout/main.xml`, 50 widget types).
Nothing was changed in this audit.

## 1. Where layout XML is made

There is no `LayoutBuilder` class, and DesignActivity writes no XML: it calls `yq`, which runs these.

| File | What it does |
|---|---|
| `a/a/a/Ox.java` | The layout writer. `writeRootLayout` (root, toolbar / FAB / drawer wrappers), `writeWidget` (tag of each view and the Material 3 swaps, lines 270-300; width / height / id / padding / margins), `writeTextAttributes`, `writeBackgroundResource`, `writeImgSrcAttr`, `k()` (per-type attributes: checked, progress / max, firstDayOfWeek …), `readAttributesToReplace` (the view's injected attributes win) |
| `a/a/a/Nx.java` | XML element builder (tag, attributes, children, raw injected text) |
| `com/sketchware/ai/project/M3Widgets.java` | Material 3 decisions per generation: filled / tinted `SketchButton`, `MaterialSwitch` / `MaterialCheckBox` / `MaterialRadioButton`, `MaterialCardView`, `MaterialToolbar`, the outlined `TextInputLayout` around `SketchTextField` (`wrapEditText`, line ~400), `scanCode` (code that touches a widget keeps it plain), helper class sources |
| `a/a/a/yq.java` | Writes every file: layouts (~line 786), `styles.xml` / `colors.xml` (~930-985: AppTheme, `AppTheme.Fab`, `AppTheme.TextField`), helper classes, `provider_paths.xml` |
| `a/a/a/Mx.java`, `com/sketchware/ai/project/M3Palette.java` | values XML builder; Material 3 colour roles (`values/` + `values-night/m3_colors.xml`) |
| `dev/aldi/sayuti/editor/injection/AppCompatInjection.java` | AppCompat Manager attributes for toolbar / app bar / collapsing layout |
| `a/a/a/Jx.java`, `a/a/a/Lx.java` | Java field types and `findViewById` lines, which must match the XML tag (MaterialSwitch: Jx 684-709, Lx 175) |
| `CommandBlock.applyCommands` | XML command blocks run on every generated XML file |
| Design canvas (preview only) | precompiled `com.besome.sketch.editor.view.item.Item*` (ItemProgressBar, ItemSeekBar …); source ItemButton / ItemEditText / ItemSwitch / ItemCheckBox / ItemLinearLayout; `editor.DesignTheme`, `editor.M3Canvas` |
| Property panel | precompiled `com.besome.sketch.editor.property.ViewPropertyItems` (which rows exist); source `Property*Item` rows and `ui.ObsidianPropertyPanel` (look); `com.besome.sketch.beans.ViewBean` (stored fields: `progressStyle`, `indeterminate`, `max`, `progress`, `inject` …) |

## 2. What a Material 3 project's layout gets today (fixture 908, v1.9.4)

| Palette widget | Generated tag | Material 3? |
|---|---|---|
| Button | `<package>.SketchButton` (MaterialButton), or plain `Button` when code / style / image keeps it | yes (filled) |
| EditText | `TextInputLayout` (outlined, `AppTheme.TextField`) + `SketchTextField` | yes |
| Switch / CheckBox / RadioButton | MaterialSwitch / MaterialCheckBox / MaterialRadioButton | yes |
| CardView, Toolbar | MaterialCardView (Elevated), MaterialToolbar | yes |
| BottomNavigationView, FAB, TabLayout, AppBarLayout, CollapsingToolbar, TextInputLayout | `com.google.android.material.*` | yes: no explicit style; Theme.Material3's default styles apply (`Widget.Material3.BottomNavigationView` …) |
| SeekBar | `SeekBar` (AppCompatSeekBar through AppCompatViewInflater, tinted with the theme colours) | no |
| ProgressBar | `ProgressBar` + `style="?android:progressBarStyle"` or `…Horizontal`, `android:indeterminate` | no |
| Spinner, AutoCompleteTextView, RatingBar, TextView, ImageView | AppCompat versions through the inflater | AppCompat |
| ListView, GridView, SearchView, CalendarView, DatePicker, TimePicker, WebView, VideoView, clocks | framework | no Material equivalent with the same API |

"100 % Material 3" isn't reachable by tag swaps: Material's SearchView / SearchBar, exposed dropdown (Spinner), date /
time pickers (dialogs) and Slider have different APIs than the widgets the blocks are written for.

## 3. Findings and patch plan

| # | Item | Finding | Patch | Size |
|---|---|---|---|---|
| X1 | ProgressBar → Linear / CircularProgressIndicator | Both extend `ProgressBar` (BaseProgressIndicator), so `ProgressBar`-typed code and setProgress / setMax / setIndeterminate keep compiling. Traps: the framework circle styles are indeterminate-only (they spin although Sketchware writes `android:indeterminate="false"`), a CircularProgressIndicator with false stays a still ring; `setProgressDrawable` with a framework drawable throws in BaseProgressIndicator | Material 3 projects: horizontal style → `LinearProgressIndicator` (stored indeterminate, max, progress); circle styles → `CircularProgressIndicator` with `indeterminate="true"`; no explicit style (theme defaults, safe if Material 3 is switched off); kept a framework ProgressBar when code sets drawables / tints or the view injects style / tint (scanCode rule). Canvas keeps the old look (ItemProgressBar is precompiled) unless replaced by a source item | 1 day + fixture + layoutlib render |
| X2 | Button variants (Tonal / Outlined / Elevated / Text) | Only possible today by injecting `style=` in Custom attributes, which keeps a plain `<Button>`: an AppCompatButton with a MaterialButton style draws wrong (those styles assume MaterialButton) | (a) an injected `Widget.Material3.Button.*` style makes the tag SketchButton with that style; when Material 3 is off, map to `Widget.MaterialComponents.Button.*` (an explicit Material 3 style under a MaterialComponents theme throws InflateException, CLAUDE.md §4). (b) a *Style* row (Filled / Tonal / Outlined / Elevated / Text) stored as that inject, so no new project field; ViewPropertyItems is precompiled: the row is added from source the way the existing Property*Item rows are, or by subclassing. (c) canvas: M3Canvas / ItemButton draw the four looks | 1.5 days |
| X3 | TextInputLayout counter / helper text / password toggle | The outlined box gets the hint only; no property for counter or helper text | (a) Attributes injected on the EditText that belong to the box move to it, like the layout attributes already do: `app:helperText`, `app:counterEnabled`, `app:counterMaxLength`, `app:endIconMode`, `app:prefixText`, `app:suffixText`, `app:startIconDrawable`, `app:errorEnabled`; an injected `android:maxLength` alone gives no counter. (b) Password fields (`inputType` password) → `app:endIconMode="password_toggle"`: adds an eye icon to existing projects, so your call (default on for new projects only?). (c) Blocks setError / setHelperText routed to the box (SketchTextField already routes setHint) | 1 day |
| X4 | BottomNavigationView | Already the Material class; Theme.Material3 gives it the M3 style (surface container, active indicator) | none; a layoutlib render with a 3-item menu to confirm | 1 h |
| X5 | SeekBar → Slider | Slider is not a SeekBar (BaseSlider extends View; float value, addOnChangeListener). Swapping the tag breaks every SeekBar block and the onProgressChanged / tracking events | a new **Slider** palette widget for Material 3 projects (value / from / to / step properties; set / get blocks; value-changed and touch events), SeekBar left as is. Needs a new ViewBean type, palette icon, canvas item, class info, events (oq / Lx), field types (Jx) | 3-4 days |
| X6 | Direct XML editing (v1.9.3-deep-audit §3) | Not started. The plan stands: XmlToViews parser → proof by regenerating through Ox (refuse what doesn't come back exactly) → XmlEditorActivity (sora, XML) → fixture: every template layout opens and saves unchanged, edits map back → layoutlib render | after X1-X3, because the proof compares with Ox's output and those change it | 3-4 days + phone test |

Each item ships with: a fixture built on the ART harness, Export AAB, Export to Android Studio built with Gradle, layoutlib
renders in light / dark (empty, filled, disabled states), and the old-project check (a project made before the change
generates the same XML unless it uses the new option).

## 4. v1.9.5 (owner's decisions of 2 Nov) and the order after it

1. **Storage split** (confirmed): a *Photo picker* block that needs no permission. With AppCompat:
   `ActivityResultContracts.PickVisualMedia` / `PickMultipleVisualMedia` (registered as a field before the activity
   starts; Android 13+ system picker, the Play services backport or `ACTION_OPEN_DOCUMENT` below); without AppCompat:
   `MediaStore.ACTION_PICK_IMAGES` on 33+, `ACTION_GET_CONTENT` below; an event with the picked URIs. The group now called
   Storage/Media becomes *Full media access* (READ_MEDIA_IMAGES / VIDEO / AUDIO / VISUAL_USER_SELECTED, for gallery and
   file-manager apps), with a line in its (i) text about Play's photo and video policy.
2. **Searchable permission picker**: the permission slot opens a dialog (ExtraMenuBean, source) listing the groups first,
   then every `android.permission.*` of the bundled android-37 jar's `Manifest.permission`, filtered as you type, with
   *Custom permission* for a typed name. `SketchPermission` maps a chosen legacy name to its group at run time
   (READ_EXTERNAL_STORAGE → media permissions on 33+, BLUETOOTH → CONNECT / SCAN on 31+), and the manifest gets the
   group's entries with maxSdkVersion as in v1.9.4.
3. Then X1, X2, X3 (+ X4 render), X5, X6.

File blocks: v1.9.4 left their READ / WRITE declarations without maxSdkVersion (that is what stays safe on Android
11-12); only the permission blocks' entries carry maxSdkVersion. Unchanged in v1.9.5.
