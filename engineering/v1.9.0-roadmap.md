# v1.9.0: palette audit and execution roadmap (25 Oct 2026)

Request (owner, 25 Oct 2026): palette audit with 2026 dependency upgrades (Tier 1 bumps, Tier 2 Material 3 tags, Tier 3
components), a project importer modelled on `morluto/rea`, an (i) blueprint for every widget and component, and the base
for Kotlin / Jetpack Compose blocks. This file is the audit (what was read, from where) and the plan. Nothing here is
built yet.

How it was checked: every library's published AAR/POM/module file read directly from Google Maven, Maven Central and
JitPack (`AndroidManifest.xml` minSdk, `aar-metadata.properties` minCompileSdk, class-file major, `.kotlin_module`
presence, runtime dependencies); APIs compared with `javap` on the published classes; the generator's calls read from the
source and the precompiled `Fx`/`Lx` strings. The deep web research run could not start (account limit) and is not part
of this file.

The on-phone toolchain decides every verdict: user projects compile against the bundled **android.jar API 34** with ECJ
(Java 11), kotlinc **1.7.10** (reads Kotlin metadata up to 1.8), D8 8.11.18, aapt2 2.20; built-in libraries must have
minCompileSdk <= 34, minSdk <= 21, Kotlin metadata <= 1.8, class files <= 55.

## 4. `morluto/rea` and the project importer

What the repositories are (cloned 25 Oct 2026, both MIT):
- **morluto/rea** ("REA: Reverse Engineer Anything", npm `rea-agents` 6.8.0): a Node.js (22+) **MCP server** that lets
  a desktop agent drive external analysis tools (Hopper/Ghidra/IDA, **apktool**, **JADX**, Frida, a browser) and returns
  findings with evidence and stated unknowns. Its Android part decodes APKs with apktool/JADX and parses the decoded
  manifest with bounded limits (`src/android/AndroidManifestComponents.ts`: activities, services, receivers, providers,
  intent filters, permissions, each with size caps against hostile input).
- **mytechnotalent/rea** (Reverse Engineering Assistant 7.1.0): a pure-Rust offline CLI/MCP for binaries (ELF/PE,
  firmware, model files), with reports.

Neither runs inside an Android app or parses Android Studio *source* projects; nothing of their code moves into the APK.
What carries over are working principles, now part of the engine skill:
1. **Evidence and unknowns**: every imported element is reported as mapped (with the block/view it became), kept as
   source (add-source / custom view / raw XML injection) or not imported, with the reason. Nothing is dropped silently.
2. **Bounded parsing**: size and count limits on every input (files, nodes, attributes, string bytes), like REA's
   manifest limits; a hostile or huge project fails with a report, never an OOM.
3. **Deterministic tools first, inference second**: real parsers decide; heuristics only propose and are marked as such.
4. **Round-trip proof** (already the Java editor's rule): an import is kept only when the code generated again from the
   blocks compiles, and where it claims equivalence, equals what was imported.

Importer design (Android Studio / GitHub project → Sketchware AI project). Input is a **source** project (zip or a git
clone of a public repository; JitPack/Maven only for dependencies, per the network rule):
- `settings.gradle(.kts)` / `app/build.gradle(.kts)`: read as text (never executed): applicationId, min/target SDK,
  dependencies → the Library Resolver (built-ins recognised, others downloaded by coordinate), unknown plugins reported.
- `AndroidManifest.xml` (plain XML in a source project): activities → project files, permissions → permission manager,
  launcher activity; bounded like REA.
- `res/layout/*.xml`: tag → palette type (`ViewBeans` map incl. Material classes), attributes → ViewBean properties;
  unknown tags/attributes → inject text or a custom view, reported.
- `res/values`, `drawable`, fonts, `assets`: copied into the project's resources.
- Java (`*.java`): parsed with **JavaParser** (Apache-2.0/LGPL, pure Java, runs on ART) into an AST; `onCreate` and
  listener patterns → events; statements → blocks through the v1.8.9 `StatementBlocks` (exact-regeneration rule), the
  rest add-source; other classes → the project's Java files.
- Kotlin (`*.kt`): kept as project Kotlin files (the build already compiles them with kotlinc 1.7.10). Mapping Kotlin to
  blocks needs the Kotlin PSI (present in the APK's embedded compiler) and the Kotlin block generator of section 6:
  after that, not before.
- Export to Android Studio (since v1.8.5) is the other direction: import ∘ export must give back an equivalent project
  for every fixture (new check).

## 5. (i) blueprint for every widget and component

A data model (JSON in the APK's assets, one entry per palette type and component), filled from sources the IDE already
has, not hand-written prose: the block specs and opcodes per type (`lq`, the block palette), the events the generator
offers (`eC.i`, event lists), the permissions the permission manager adds, the built-in libraries a type pulls in
(`BuiltInLibraries`), and the Material 3 mapping (section 2). Shown in the view editor's property panel and the
component dialog: connections (views ↔ components ↔ events), the block tree as categories (Control, Operator, Math,
Variable, View, Component) with which plugs into which, and manifest permissions. A test checks that every palette type
and component has an entry and that every opcode named exists.

## 6. Polyglot blocks and Jetpack Compose

- **Language-neutral blocks**: today `a.a.a.Fx` (precompiled) turns blocks into Java text. Step 1 is an intermediate
  representation of a block chain (the v1.8.9 mapper already pairs every statement with its block); step 2 a Java emitter
  that reproduces Fx byte for byte on all fixtures (proof by comparison, as the source map does); step 3 a Kotlin emitter
  for activities marked Kotlin, compiled by the embedded kotlinc 1.7.10. Kotlin activities need their own generated
  frame (Jx in Kotlin) and the source map/Java editor for Kotlin.
- **Compose on the phone**: current Compose needs the Kotlin 2 compiler plugin and compileSdk 35+, so it can't run here.
  The only combination matching the embedded **kotlinc 1.7.10** is the 2022 line: Compose compiler **1.3.1** (Google
  Maven; Android's compatibility map pairs 1.3.0/1.3.1 with Kotlin 1.7.10, to be confirmed by running it), Compose
  runtime/UI **1.3.3** and Compose Material3 **1.0.1** (all minSdk 21, **minCompileSdk 33**, kotlin-stdlib 1.7.10,
  coroutines 1.6.4: within the toolchain). A prototype must prove kotlinc with the compiler plugin runs on ART within
  memory, then `[Composable: Column/Row]` container blocks generate `@Composable` Kotlin hosted in a `ComposeView`.
  It would be an old Compose (no newer APIs, no current Material 3 components); say so before building it.
